# ۲۵ — ابزار شبیه‌سازی متلب (`ports/matlab/+simlab`)

## چرا این ابزار

تنظیم در متلب چون تکرارش چند ثانیه طول می‌کشد؛ فلش کردن با C چون چیزی است
که STM32 اجرا می‌کند. بین این دو جایی است که ضریب‌ها اشتباه تایپ می‌شوند،
فیلتر مشتق فراموش می‌شود، و حلقه‌ای که در شبیه‌سازی عالی بود روی برد رفتار
دیگری دارد.

`+simlab` روی `+pidx` سوار است — همان پورت کنترل‌کننده که **۵۰۲ ردیف از ۵۰۲
ردیف** با کتابخانهٔ C منطبق است — و بخش‌هایی را اضافه می‌کند که یک جلسهٔ
تنظیم واقعاً لازم دارد.

```matlab
cd <repo>/ports/matlab
simlab_setup
simlab_demos.demo_quick      % تور پنج‌دقیقه‌ای
```

سه راه ورود، یک موتور در زیر هر سه:

| | | |
|---|---|---|
| `simlab_wizard` | جریان کاری کنسولی | روی ssh و در Octave هم کار می‌کند |
| `simlabApp` | رابط گرافیکی پنج‌زبانه | `uicontrol` کلاسیک، بدون App Designer |
| `simlab_demos.*` | مطالعات اسکریپتی | مرجع اتوماسیون |

## ۱. پلنت سه مرحله است، نه یک تابع تبدیل

```
u_cmd -->[ محرک ]--> u_plant -->[ مدل ]--> y_true -->[ سنسور ]--> y_meas
```

در مسیر رفت: اشباع، ناحیهٔ مرده، محدودیت نرخ، و دقت PWM. در مسیر برگشت:
نویز، کوانتیزاسیون ADC، ناحیهٔ مرده، تأخیر انتقال، گیر کردن سنسور و افتادن
نمونه. **همه خاموش‌اند** مگر آنکه روشنشان کنید، پس یک مدل خالص دقیقاً یک
پلنت خالص است و `yMeas == yTrue` بیت‌به‌بیت.

`yTrue` و `yMeas` هر دو در هر نمونه ثبت می‌شوند. فاصلهٔ این دو خط روی نمودار
**همان** زنجیرهٔ سنسور شماست — همان چیزی که شبیه‌سازی با تابع تبدیل بی‌صدا
نادیده می‌گیرد.

مدل‌ها: `fopdt` (دقیق)، `linear` (هر tf، گسسته‌سازی ZOH)، `dc_motor` (همان
موتور `examples_stm32/03_motor_speed` با همان ثابت‌ها و همان زیرگام)، و
`custom` (تابع `f(x,u,dt)` خودتان).

```matlab
pl = simlab.Plant.presets('heater');       % K=2, tau=45s, L=12s, ADC 12 بیتی
pl = simlab.Plant('fopdt', 'k', 2, 'tau', 45, 'l', 12);
pl.setActuatorLimits(0, 100);
pl.setNoise(0.15);
pl.setAdcBits(12, 0, 300);
```

## ۲. سناریو یک فیلم‌نامه است، نه یک پله

```matlab
sc = simlab.Scenario('اجرای من', 60);
sc.setpoint(0, 0);
sc.setpoint(150, 1);
sc.loadStep(0.004, 20);       % بار می‌نشیند
sc.noise(0.4, 30);            % سنسور پرنویز می‌شود
sc.stuck(25, 40);             % سنسور می‌چسبد
sc.stuck([], 50);             % و برمی‌گردد
r = simlab.Sim(plant, ctrl, sc).run();
simlab.plot(r);
```

`metrics()` خودش اولین پلهٔ setpoint را پیدا می‌کند و از آن‌جا اندازه
می‌گیرد، پس یک تابع هم پاسخ پلهٔ ساده را می‌سنجد هم فیلم‌نامهٔ چهل‌رویدادی.
هر متریک که پنجرهٔ اندازه‌گیری نداشته باشد `NaN` است — هرگز صفرِ ساختگی.

ترتیب نمونه‌برداری همان ترتیب ISR است: پلنت با فرمان **دورهٔ قبل** جلو
می‌رود، بعد کنترل‌کننده نتیجه را می‌خواند. برعکسش یک نمونه تأخیر مردهٔ
اضافی به هر مطالعه تزریق می‌کند، و تست این را با بررسی اینکه ترتیبِ غلط
پاسخِ **متفاوتی** می‌دهد تأیید می‌کند — وگرنه تست به دلیل اشتباه قبول می‌شد.

## ۳. تنظیم خودکار، همان کد C است

`+simlab/AutoTune` پورت خط‌به‌خط `src/pid_autotune.c` است. عمدی: ضریب‌هایی
که فلش می‌کنید روی هدف از `pid_autotune.c` می‌آیند، پس یک autotune آماده
اعدادی می‌دهد که روی برد به هیچ چیز corrispond نیستند.

همه‌چیز حفظ شده، از جمله بخش‌های خوشایندنبودش:

- تصحیح هیسترزیس `Ku = 4h / (π √(a² − ε²))`؛
- بازوی گشتاور **نقطهٔ میانی** در برازش پله. اگر بازو در انتهای بازه نمونه
  گرفته شود، گشتاور اول به اندازهٔ `te·dt/2` به ازای هر واحد `dy` کوتاه
  می‌ماند — کسری که با طول آزمایش **بزرگ‌تر** می‌شود، یعنی آزمایش طولانی‌تر
  و دقیق‌تر مدل **بدتری** می‌داد؛
- امتیاز کیفیت، و دروازهٔ `quality < 50` که از برگرداندن ضریب‌های
  بی‌اعتبار خودداری می‌کند؛
- کف ۲۰ نمونه در هر دوره که نوسانی را که نرخ نمونه‌برداری نمی‌تواند تفکیک
  کند رد می‌کند.

و دو یافته‌ای که مطالعهٔ C مستند کرده و اینجا به‌جای پنهان‌کردن، **تست**
می‌شوند:

> **رله همیشه Ku را کمتر برآورد می‌کند**، تا ٪۲۵− حتی با نویز صفر. تئوری
> تابع توصیف دامنهٔ *مولفهٔ اصلی* را می‌خواهد؛ هر پیاده‌سازی عملی *قله* را
> اندازه می‌گیرد و یک چرخهٔ حدی هارمونیک دارد. خطا در جهت امن است — ضریب‌ها
> کم می‌آیند، پس حلقه کُند می‌شود نه ناپایدار.

> **برآورد تقریباً دقیق بهره هم می‌تواند گمراه کند.** معیار سکونِ آزمایش پله
> (در ٪۰٫۵ *برآورد لحظه‌ای*، به‌علاوهٔ شیب صاف) وقتی آزمایش از یک بایاس
> غیرصفر شروع شود در حدود دو‌سوم مسیر فعال می‌شود، پس `K` زیاد از آب درمی‌آید
> در حالی که `T` و `L` در چند درصد خطا می‌نشینند. کتابخانهٔ C هم دقیقاً همین
> رفتار را دارد؛ تست عدد را میخکوب می‌کند تا یک «بهبود» بعدی نتواند بی‌صدا
> عوضش کند.

یک قاعدهٔ FREQ که مدل FOPDT بگیرد **رد** می‌شود، نه تبدیل: یک نقطه روی منحنی
نایکوئیست سه پارامتر مدل را تعیین نمی‌کند و هیچ تبدیل درستی بین این دو وجود
ندارد. بررسی پیکربندی این جفت‌نشدن را **پیش از** اجرای آزمایش می‌گیرد، پس
تشخیص هیچ هزینه‌ای ندارد به‌جای یک تنظیم دومینیه‌ای که داده‌اش دور ریخته شود.

## ۴. استحکام: سؤالی که تصمیم فلش‌کردن را می‌گیرد

پاسخ پله روی یک مدل کامل، عددی بدون نوار خطا است. مدل شما از شناسایی آمده و
شناسایی ۱۰ تا ۳۰ درصد خطا دارد.

```matlab
mc = simlab.monteCarlo(plant, gains, struct('nRuns', 60, 'spread', 2));
```

`compareRules` هر دو رتبه‌بندی را کنار هم می‌دهد، چون تقریباً برعکس هم‌اند —
همان یافتهٔ `sim/sim_robust.c` (۸۱۰ اجرا، ρ = −۰٫۵۸۶):

```matlab
cr = simlab.compareRules(plant, struct('mode', 'robust', 'nRuns', 30));
simlab.plotRules(cr);
```

پیشنهاد ابزار **کمترین IAE نیست**. سریع‌ترین قاعده‌ای است که در ≥٪۹۰ پلنت‌های
مختل‌شده دوام آورده، و متن همین را صریح می‌گوید.

حاشیه‌های حوزهٔ فرکانس از `sensitivity` می‌آیند که به هیچ تولباکسی نیاز ندارد
و فرض‌های خودش را اعلام می‌کند:

```
L(jω) = C(jω) · G(jω) · exp(−jω(L + dt/2))
```

آن `dt/2` نگه‌دارندهٔ مرتبهٔ صفر است. حذفش هر حلقهٔ گسسته را مقاوم‌تر از آنچه
هست نشان می‌دهد و خطایش با `dt` بزرگ می‌شود — در `dt = 0.5 s` روی حلقه‌ای که
نزدیک ۱٫۷ rad/s قطع می‌کند، ۲۵ درجهٔ فاز است که حساب نکرده‌اید.
`test_sensitivity.m` دقیقاً همین را چک می‌کند.

## ۵. خروجی برای STM32CubeIDE

```matlab
out = simlab.exportSTM32(plant, cfg, struct('symbol', 'heaterLoop', ...
      'profile', 'PROCESS', 'result', r, 'sens', s));
```

دو فایل نوشته می‌شود: یک هدر با همهٔ عددها به‌صورت `#define` همراه واحد و
متریک‌های اندازه‌گیری‌شده به‌صورت کامنت، و یک سورس با `<symbol>_init()` و
`<symbol>_tick(y)`.

**هیچ کد HAL تولید نمی‌شود.** اینکه کدام تایمر، کدام کانال ADC و کدام ISR
مالک حلقه است تصمیمی دربارهٔ برد شماست، و تولیدکننده‌ای که حدس بزند کدی
می‌دهد که به‌هرحال باید بخوانیدش.

اگر قابلیتی در پروفایل انتخابی نباشد، در فایل به‌صورت `NOT EXPORTED` علامت
می‌خورد و در خروجی هم فهرست می‌شود — حذف بی‌صدای یک قابلیت بدترین نتیجهٔ
ممکن برای یک export است.

اتصال در پروژهٔ شما:

```c
#include "pidx_tuning_heaterLoop.h"

heaterLoop_init();                 /* یک‌بار، بعد از HAL_Init() */

void TIM2_IRQHandler(void) {
    if (LL_TIM_IsActiveFlag_UPDATE(TIM2)) {
        LL_TIM_ClearFlag_UPDATE(TIM2);
        float u = heaterLoop_tick(read_sensor());
        write_actuator(u);
    }
}
```

## ۶. راستی‌آزمایی

```matlab
cd simlab_tests
test_suite
```

ادعاهای عددی با `simlab_tests/c_reference.csv` مقایسه می‌شوند که
`tools/matlab_ref/matlab_ref.c` آن‌ها را با اجرای **همان سناریوها روی
کتابخانهٔ C** در دقت double تولید کرده. کتابخانهٔ C اوراکل این ریپوزیتوری است
— همان چیزی که STM32 اجرا می‌کند — پس اختلاف یعنی متلب اشتباه است، نه اینکه
تلورانس تنگ است.

```bash
cd tools/matlab_ref && make run     # بازتولید مرجع
python3 tools/matlab_lint.py        # بررسی ساختاری، بدون نیاز به مفسر
python3 tools/check_export_identifiers.py   # هر نام PID_* صادرشده در هدرها هست
```

### حدِ صادقانه

- **در جایی که این ابزار نوشته شد هیچ مفسر MATLAB یا Octave در دسترس نبود.**
  اوراکل C ساخته و اجرا شده و اعداد مرجع داخل تست‌ها واقعی‌اند؛ اما خودِ کد
  متلب توسط نویسنده‌اش اجرا نشده. پیش از اعتماد به هر عدد `test_suite` را
  اجرا کنید.
- `simlab.sensitivity` بخش **خطی** حلقه را توصیف می‌کند. اشباع، ناحیهٔ مرده و
  کوانتیزاسیون در نمودار بود نیستند؛ `plant.analysisCaveats()` می‌گوید کدام‌یک
  را پلنت شما دارد و نمودارها و گزارش JSON همان را حمل می‌کنند.
- `Plant('linear')` به `c2d` (Control System Toolbox) نیاز دارد. `fopdt`،
  `dc_motor` و `custom` دستی انتگرال‌گیری می‌شوند و به چیزی نیاز ندارند.
