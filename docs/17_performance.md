# ۱۷ — کارایی و اندازه

## ⚠️ اول از همه: این اعداد از کجا آمده‌اند

در محیطی که PIDX نوشته شد، **`arm-none-eabi-gcc` نصب نبود**. بنابراین:

- همهٔ اعداد زمان و اندازهٔ این صفحه روی **x86-64** اندازه‌گیری شده‌اند.
- هیچ عدد Cortex-M در این مستندات **اندازه‌گیری** نیست. هر جا عددی برای
  Cortex-M می‌بینید، صریحاً **«هدف طراحی»** برچسب خورده.
- برای عدد واقعی، `bench/bench_dwt.c` را روی برد خودتان اجرا کنید.

**عدد ساختگی گزارش نمی‌شود.** این تنها راه صادقانه بود.

## زمان اجرا (x86-64، `-O2`)

از `bench/bench_host.c` — ۲۰۰٬۰۰۰ تکرار، ۷ اجرا، آمارهٔ **کمینه**، سربار
حلقه کم‌شده:

| مسیر | ns/call | FLOPs | نسبت |
|---|---|---|---|
| `PID_UpdateFast` | ~۲.۹ – ۳.۰ | ۱۲ | ۱.۰۰× |
| `PID_UpdateFast` (P-only) | ~۲.۹ – ۳.۰ | ۱۲ | ~۱.۰۰× |
| `PID_Update` | ~۱۱.۶ – ۱۲.۵ | ۱۸ | ~۴.۱× |
| `PID_UpdateDt` (dt ثابت) | ~۱۲.۱ – ۱۲.۳ | ۱۹ | ~۴.۱× |
| `PID_UpdateDt` (dt متغیر) | ~۱۶.۶ – ۱۶.۹ | ۲۸ | ~۵.۷× |
| `PIDq_Update` (Q15) | ~۷.۰ – ۷.۷ | **۰** | ~۲.۵× |
| `PID_Cascade_Update` (۲ حلقه) | ~۴۱.۰ – ۴۱.۵ | ۴۰ | ~۱۴× |

> **چرا بازه و نه یک عدد؟** شش اجرای پشت‌سرهم روی همین ماشین، `PID_Update`
> را بین ۱۱.۶۳ و ۱۲.۲۷ نانوثانیه داد. نوشتن «۱۲.۱۶» یک **دقت کاذب** است.
> نسبت‌ها پایدارند و همان‌ها به تارگت تعمیم می‌یابند.

**چیزهایی که این جدول می‌گوید:**

۱. **مسیر سریع واقعاً ۴ برابر سریع‌تر است.** اگر ISR شما ۲۰ کیلوهرتز است،
   این تفاوت واقعی است.

۲. **P-only همان زمان پیکربندی کامل را می‌گیرد.** `PID_UpdateFast` عمداً
   branchless است: زمان اجرای **ثابت** برای یک ISR سخت‌بلادرنگ از چند سیکل
   صرفه‌جویی ارزشمندتر است. این ردیف شاهد آن ادعاست.

۳. **`dt` متغیر ۳۸٪ گران‌تر است** چون `pidp_recompute()` سه تقسیم دارد. اگر
   نرخ شما ثابت است، `PID_Update` را استفاده کنید نه `PID_UpdateDt`.

۴. **روی x86-64 نسخهٔ Q15 کندتر از float است** — چون این CPU یک FPU عالی
   دارد. **این را به تارگت تعمیم ندهید.** روی Cortex-M0 که FPU ندارد، نسبت
   برعکس می‌شود.

## اهداف طراحی برای Cortex-M4F

**اینها هدف‌اند، نه اندازه‌گیری.**

| مسیر | هدف (سیکل) |
|---|---|
| `PID_UpdateFast` | < ۱۰۰ |
| `PID_Update` معمولی | < ۱۶۰ |
| `PID_Update` کامل | < ۳۲۰ |
| `PID_UpdateDt` با dt متغیر | +۹۰ |
| `PID_AutoTune_Update` | < ۶۰ |
| Flash هسته (`-Os`) | < ۲.۰ KB |

`bench/bench_dwt.c` همین جدول را با ستون «measured» پر می‌کند و خودش
PASS/OVER می‌زند.

## اندازه‌گیری روی سخت‌افزار خودتان

```c
#include "bench_dwt.c"     /* یا به پروژه اضافه‌اش کنید */

int main(void)
{
    SystemClock_Config();
    bench_dwt_run(168000000U);   /* فرکانس هسته */
}
```

نکاتی که در آن فایل رعایت شده و شما هم باید رعایت کنید:

- **DWT روی Cortex-M0/M0+ وجود ندارد.** فایل با `#error` رد می‌شود.
- روی بعضی قطعات `DWT_LAR` باید unlock شود.
- روی بعضی قطعات CYCCNT تا اتصال دیباگر در reset می‌ماند — کد **تأیید
  می‌کند** که شمارنده واقعاً جلو می‌رود و اگر نه، صریحاً می‌گوید به‌جای
  گزارش صفر.

## تکنیک‌های بهینه‌سازی به‌کاررفته

۱. **پیش‌محاسبهٔ ضرایب** — هیچ تقسیمی در مسیر داغ. تنها تقسیم‌کننده
   `pidp_recompute()` است.
۲. **بیت‌ماسک `features`** — `if ((features & PID_FEAT_ADVANCED_MASK) == 0)`
   یک شاخه کل بلوک پیشرفته را رد می‌کند.
۳. **`static inline`** برای clamp و isfinite در هدر.
۴. **ترتیب فیلدها بر اساس دمای دسترسی** — فیلدهای داغ در ۶۴ بایت اول.
۵. **بدون ارتقای `double`** — همهٔ ثابت‌ها پسوند `f`، و
   `-Wdouble-promotion -Werror` این را تضمین می‌کند.
۶. **بدون `math.h` در مسیر داغ** — `sqrtf` فقط در auto-tune.

## نکتهٔ روش‌شناسی: چرا «کمینه» نه «میانگین»

در benchmark آمارهٔ گزارش‌شده **کمینه** است. نویز زمان‌بندی فقط زمان
**اضافه** می‌کند؛ پس سریع‌ترین اجرای مشاهده‌شده نزدیک‌ترین به هزینهٔ واقعی
است. میانگین، بار پس‌زمینهٔ ماشین را اندازه می‌گیرد نه کد را.

و مهم‌تر: **هر نتیجه در یک `volatile` جمع می‌شود.** بدون آن، در `-O2`
کامپایلر کل حلقه را حذف می‌کند و عدد چند پیکوثانیه گزارش می‌شود.
